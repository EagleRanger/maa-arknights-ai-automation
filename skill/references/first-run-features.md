# First-run choices, published defaults and private account settings

## Preserve the released default

Use the existing installed/released daily-cleanup and progression chain. Keep
its established order, launcher, outcome/retry logic, resource policy and cleanup.
This update adds optional interfaces; it is not permission to redesign that
chain, automatically create schedules, or migrate a proven per-stage loop to
MAA's list mode. Resolve the actual installed release manifest/baseline before
merging an update. A source reference directory alone is not a full runtime.

On first installation explain in ordinary language what the published chain
does and confirm machine/account binding plus resource boundaries. Present the
supported optional functions, distinguishing verified behavior from test
adapters and not-yet-integrated native capabilities. The user need not configure
every module. Retain their existing explicit choices; do not force an already
configured account through setup again.

Label a working but incompletely validated feature **Beta 测试** in release
notes and identify the specific step tested. An optional beta does not delay
the established daily workflow. A read-only planner is not a purchase feature.

For later special settings, tell the recipient to ask **their own AI** to adjust
the corresponding interface/profile. Examples are a named operator/skill order,
voucher product/budget choices, farming goals and base scheduling. Apply only
the requested local change, validate the actual consumer, and keep the rest of
the published default chain intact. No daily repeated approval or new setup
gate is added. A disabled/unconfigured optional module skips itself, not daily.

## Three different kinds of data

| Kind | Shared with recipients | Local handling |
| --- | --- | --- |
| Generic mechanisms | Module contract, input/output meaning, evidence and recovery, shipped default chain | Maintained upstream; compare changes before updating |
| User choices | Only empty/example schemas, never publisher values | Private editable contract/profile; recipient AI compiles them into the actual runtime settings |
| Account facts | Never | Verified client/server + game UID; real progress, period, screenshots and receipts in the private account store |

In particular, do not distribute the publisher's named operators, mastery
order, module progress, inventories, ticket preferences, stage holds, emulator
port/path, screenshots, logs or tokens. Do not infer account completion from
a release package. A user's manual choice is a preference, not proof of level
or ownership. New account facts start unknown.

## Optional interface choices

- Operator development: exact operator, skill and target mastery; module mission
  name and whether **only missions** or also unlocking/upgrading is requested.
  Keep currently running training and verify actual completion before advancing.
- Vouchers: token conversion, green-ticket product scope, standard versus kernel
  yellow-ticket permits, full-bundle budget, explicitly named operator exchanges,
  red-ticket product scope. Do not inherit somebody else's selection.
- Other supported interfaces: retain the shipped daily/event/base/recruit/shop/
  reward/cleanup interfaces; roguelike/other long runs remain separate goals,
  never an automatic replacement for an uncompleted daily task.

Record the chosen modules, resource limits and configuration revision in the
existing private contract/profile. Use [account-progress.md](account-progress.md)
for actual account facts, not another contradictory Markdown completion list.
When new optional functionality arrives, explain only that addition; do not
reset previously accepted setup. Updates preserve user changes using
[release-notices-and-local-merge.md](release-notices-and-local-merge.md).
