# Evidence-driven continuation and closeout

Use this reference for long or interrupted runs, phased events, temporary MAA changes, and final reconciliation. These are adapter requirements and control methods, not a bundled production implementation or permission to start a game.

## Recover the unfinished scope, not the whole run

Resolve the current approved handoff for the requested domain. Reconcile its targets and cumulative retry/resource budget with actual effects before resuming. A new technical run identifier does not erase completed work, reset a battle budget, or create a new business objective. Missing or ambiguous authority stops the affected action; independent authorized domains may continue.

Separate newly verified completion, previously verified completion retained without replay, and unfinished targets. Preserve original receipts and evidence. Do not rerun a stage or a daily chain merely to repair a report or prove a parser fix.

## Phase identity and completed-node protection

- Distinguish the event identity, exact internal stage, displayed label, mode, opening prerequisite, battle deadline, and reward deadline. A displayed number or internal-name suffix alone is not a unique stage identity.
- The currently open batch is not the entire event. Freeze verified nodes individually; a newly open batch must not erase older completion, and an earlier completed batch must not hide future work.
- Use the existing receipts and approved source manifest instead of inventing another completion database. Preserve original observation times. A metadata repair must not replace a screenshot's time with the repair time.
- A calendar refresh can succeed while omitting a new event. A current game surface showing an event triggers bounded identity/source verification, not an unsupported inference that no event exists or automatic fallback farming.
- Opening dates and countdowns produce candidates. Verify the current detail page, exact identity, mode and available action before entry. Separate an unlock prerequisite from a first-clear bonus countdown.
- Bind completion to the selected target's settlement and returned-map/detail state. A neighboring node's COMPLETE text must not complete the selected node. Queue idle while the game still visibly fights calls for non-contending observation, not a map click or a second job.

Completed mainline remains closed until a new-mainline signal or an explicit request reopens it; do not make full rescans the default daily task. Tutorial stages remain a manual boundary.

## Recover decisive evidence across log rotation

Keep routine polling caches bounded, but collect decisive settlement evidence across relevant rotated files using the current invocation time and available process/session/task identifiers. Retain timestamps and source-line pointers; do not keep entire large logs in prompt context or memory.

A new file's short tail may omit an already executed base action. Conversely, unrelated older queues must not fill gaps in the current queue. If logs were lost or cannot be tied to the current invocation, retain unverified status. Parser repair and isolated tests do not manufacture missing execution evidence.

## Temporary configuration is a restoration transaction

When an approved adapter must temporarily change MAA configuration or resources:

1. Confirm the relevant queue is idle and the exact targets are within the approved scope.
2. Save original bytes and hashes, identify the intended patched hashes, and retain a restoration receipt before writing.
3. Recheck the idle boundary, write atomically where supported, and read back the result. On a partial installation failure, restore originals and verify restoration rather than assuming rollback succeeded.
4. At the safe restoration boundary, confirm the target MAA process has exited. Validate backup integrity and exact target paths before restoring.
5. If current bytes match neither the original nor the approved patch, stop restoration as a drift conflict; do not overwrite another actor's change.
6. Restore original bytes and compare hashes. Keep restoration failed/unverified separate from process cleanup and game completion.

This describes the verified transaction pattern, not a claim that every receiver or every older helper already implements it. A configuration round trip proves configuration integrity only, never battle completion or rewards.

## Fresh inputs are scoped by decision domain

For inventory-driven proposals, require timezone-aware observation times inside the declared sampling window: `not_before <= sync_time <= now`. Missing, stale, future, malformed or incomplete inventory stays unknown; a missing material count is not zero.

A proposed farm stage still needs current event availability, authorized resource use, verified clear/proxy state and live cost. Inventory failure freezes dependent production/farm decisions, not unrelated reward collection or an independently authorized stage. Do not transplant another computer's fixed sampling time, policy or account inventory.

## Final reporting is a conjunction of separate claims

Track business completion, owned-process cleanup, and temporary-resource restoration independently. Each needs its own evidence; `all_cleaned`, process exit, or a completed five-task chain cannot stand in for the other claims.

- Report daily and special-run scopes separately, with separate completion markers. A special zero-sanity task does not prove today's sanity was exhausted or the daily run completed.
- Name newly verified targets, preserved completed targets, unfinished targets, actual resource purpose/balance if observed, cleanup, restoration, and the next legal checkpoint. Unknown values remain unknown, not zero.
- Verify base execution, production/rotation changes, and other contracted domains independently of a generic Infrast or AllTasksCompleted marker.
- Final daily StartUp/Infrast/Recruit/Mall/Award must follow the latest real fight. A new fight invalidates an earlier final-chain closure and requires a new authorized closing chain; a report-only correction does not.
- Show a single plain-language final report whose title reflects partial/unknown status as well as success. Formatting improvements are not proof that every domain is complete.

## Receiving-project setup and acceptance

Start with the existing contract template and read-only Windows preflight. Configure local adapter paths, one controller, log/session boundaries, receipt locations, inventory sampling windows, temporary-resource restore targets, and per-domain success evidence. None of these values is supplied from the author's private account.

Exercise isolated positive and negative fixtures: rotated current vs unrelated logs, missing/future inventory, same display number in another event, queue idle while the game is still fighting, missing resource backup or unexpected drift, and special completion without daily completion. Then validate the receiver's real forward path under a bounded user-approved account task. Static fixtures, source review and a single stage's success do not certify arbitrary events, tutorial automation, all daily domains, or unattended reliability.
