# 模块化架构与渐进迁移

用于把已经能执行的本机流程拆成可独立调用、可恢复和可验证的模块。本文是公开控制契约，不附作者私人适配器，也不预设接收方的模拟器路径、账号或游戏目标。

## 先保留能工作的部分

重构时读取接收方当前批准的生产入口与源码快照，区分已验兼容路径和候选编排。版本数字较新、单测通过、某个旧单项成功，都不能证明一个新的整日控制器已经生产验收。

不因重构改掉原资源用途、定时、关卡优先级和唯一控制者。成熟 MAA/ADB 函数可保留为窄适配器；迁移的目标是边界清楚，而不是为了“全新架构”把已验能力全部重写。

## 分层结构

```text
用户目标、资源规则、当前生产配方
  └─ 编排器：选择本次获准操作、依赖、停止与续接条件
      └─ 显式装配：解析能力提供者、排序与释放
          ├─ 九个业务域：仅执行自己的操作，返回分域结果
          └─ 共用运行服务：识别、截图/OCR、有限恢复、队列与回执
外层宿主：环境准备、独占控制、显式退出领取、最终清理
同 run 事实账本：所有报告只作投影，不反向控制业务重跑
```

不是九个 AI 同时操作游戏。共享 MAA、模拟器与 ADB 仍串行，一个有效控制者；长跑与每日只共享已批准的让行规则。

## 各层不能互相吞掉职责

| 层或业务域 | 应负责 | 不应偷偷附带 |
| --- | --- | --- |
| 编排器与装配器 | 本次清单、依赖排序、能力唯一性、局部阻塞和释放 | 自创目标、自动晋升候选、重试未知效果 |
| 剿灭 | 周额度与实际结算核验 | 周期已完成后重复打 |
| 活动推进与领奖 | 当前活动身份、模式、已开放层与独立奖励 | 把某一视区完成当整期完成，或偷换活动目标 |
| 刷取 | 获准关卡、实时预算、批次结算 | 为修报告追加战斗，按请求数算完成数 |
| 主线 | 未通关节点发现、剧情/战斗分流与完成核验 | 把教学关伪装成普通作业 |
| 保全 | 周期进度、实体作业与奖励域分别核验 | 只看进过页面就写周期完成 |
| 基建 | 当前库存、计划、产品/轮班与独立验收 | 无可靠模型就声称真实产销已拟合 |
| 每日任务 | 游戏日、缺项、最后真实战斗后补领 | 任何单项都自动再跑一次完整五链 |
| 长期探索 | 原授权主题、结算边界服务与截止 | 每日结束后自动续跑肉鸽或生息 |
| 只读观察 | 读取当前证据并返回未知/已知 | 因观察失败就点击、开战或改配置 |
| 共享服务 | 同一套页面识别、限界恢复、回执基础设施 | 决定业务优先级、启动别的任务或默默收尾 |
| 外层宿主 | 环境所有权、互斥、明确退出、清理与最终交付 | 关闭不属于本次流程的环境或抢占活跃队列 |

每日任务域统一管理原有每日链和“最后一次真实战斗后是否还需补领”。业务模块成功、失败或中断后只返回结果；是否继续、退出或关闭，由本次调用者和外层宿主决定。

## 共用服务必须在最终组合里生效

仅验证 `import`、函数模块名或“安装了几个补丁”不够。旧包装器可能提前捕获函数对象，导致单项使用新验收器、整日仍调用旧验收器。

接入时检查：

- 当前生产调用链中最终的回调和已绑定调用点，是否都使用预期实现；
- 两种相关装配顺序下的实际行为，而非只检查符号名称；
- 在完整组合里输入同一份有效/无效证据，是否得到相应验收结果；
- 回执不明时保留待对账状态，不误当“动作前失败”而自动重放。

公共识别只负责读取真实新帧、判断页面与允许的有限恢复。明确加载帧可以按当前合同有界重读；稳定未知页留证，不盲点关闭按钮。不要把特定活动的坐标、按钮或数值当成跨活动不变规则。

## 单项、完整日常与续接共用模块

参考 [EXECUTION_PLAN.example.json](../templates/EXECUTION_PLAN.example.json) 和 [MODULE_RESULT.example.json](../templates/MODULE_RESULT.example.json)。它们均未激活，不携带真实任务或账号数据；只是字段示例，不是运行器。

1. 接收方绑定本机能力与验收函数；缺依赖或重复提供者先在零游戏动作检查中报错。
2. 单项只装配所需模块。例如仅领奖不应装配战斗、基建换产和全日收尾。
3. 外层明确退出时才执行本次允许的退出工作；普通单项返回不等于退出。紧急清理不自动附带游戏业务。
4. 续接读取原目标、同游戏日效果与证据；保留已完，只补缺项。效果不明先对账；已封口运行不再被重新打开点击。
5. 原定日常被维修打断时，维修完成后返回原目标，核对当天已完/未完；不能以“补丁已验收”取代本来要完成的任务。

如果生产指针、架构候选说明和历史文件里的版本不同，按当前权威入口核对各自对象；不要为文字一致而把候选升级成生产。

## 接收方验收顺序

先用假环境做零游戏调用检查：显式依赖、单项隔离、失败释放和未知效果不重试。再在用户实际需要的单项任务中验证真实页面与资源边界。最后才验证完整组合以及同一运行各报告出口的一致性。

应包含的负例：单项误调用完整日常、业务模块擅自关闭环境、重复/循环依赖、某域失败吞掉别域已完、资源证据缺失、旧日期完成记录、装配顺序改变最终验收器、记录写入失败引发重战。

每份验收绑定源码快照、入口、任务范围与证据。保留已验路径并逐段切换；不为发版再次运行已完成日常，不另建调度。跨周期产速等需要真实独立样本的能力，在样本不足时保持未知与原批准方案。
